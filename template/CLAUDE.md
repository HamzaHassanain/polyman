# CLAUDE.md — Competitive programming problem (polyman)

You are working inside a problem directory created by [polyman](https://github.com/HamzaHassanain/polyman) (`polyman new <dir>`). This is a Codeforces / Polygon-style problem package: solutions, generators, a validator, a checker, statements, and tests. The whole problem is described by a single `Config.json` at the root.

This file is the fast-path orientation for any AI agent (Claude, Cursor, Aider, Codex, etc.) working in this directory. `AGENTS.md` is a pointer to this file.

---

## 1. The mental model

A "problem" is the tuple **(statement, validator, generator(s), checker, solutions, tests)**:

- **Statement** — the human-readable problem (`statements/<lang>/*.tex`).
- **Validator** — C++ program (uses `testlib.h`) that decides whether an input file is well-formed *and* satisfies constraints. One per problem.
- **Generator(s)** — C++ programs (use `testlib.h`) that print test inputs to stdout. Many allowed.
- **Checker** — C++ program (uses `testlib.h`) that compares contestant output to the reference answer and decides OK / WA / PE. May be a built-in standard checker (e.g. `ncmp`, `wcmp`, `yesno`) or a custom one.
- **Solutions** — implementations in C++ / Java / Python, each tagged with the verdict the author *expects* (see §4). At least one main-correct (`MA`) is required.
- **Tests** — generated into `tests/` by `polyman generate` from a `generatorScript` in `Config.json`. Manual test files live in `manual/tests/`.

The whole pipeline:

```
Config.json  ──►  polyman generate ──►  tests/        (inputs)
                  polyman validate ──►  validator OK on every input
                  polyman run main ──►  reference outputs
                  polyman verify   ──►  every solution gets the verdict its tag claims
```

## 2. Directory layout

```
Config.json              The single source of truth — defines the whole problem
solutions/               Solution sources (C++, Java, Python)
generators/              C++ test generators (use testlib.h)
validator/
  val.cpp                Input validator (testlib.h)
  validator_tests.json   Self-tests for the validator (input string + expected VALID/INVALID)
checker/
  chk.cpp                Custom checker (testlib.h) — only if not using a standard one
  checker_tests.json     Self-tests (input/output/answer + expected OK/WA/PE/CRASHED)
statements/<lang>/       LaTeX fragments: legend, input-format, output-format, notes
manual/tests/            Hand-written test inputs referenced from Config.json
tests/                   Generated by `polyman generate` — do not hand-edit, they get overwritten
testlib.h                Required for compiling validator/generator/checker. Run `polyman download-testlib` if missing.
```

## 3. The two commands you will use most

```bash
polyman generate --all        # regenerate every test from the script
polyman verify                # full pipeline: generate, validate, run all solutions, check tags
```

Other useful ones:

```bash
polyman list solutions               # what solutions exist + tags
polyman list generators
polyman list checkers                # standard testlib checkers available
polyman list testsets

polyman generate --testset tests --index 5     # one test
polyman validate --all                          # validator over every input
polyman run main --all                          # run a specific solution against every test
polyman test validator                          # run validator self-tests
polyman test checker                            # run checker self-tests
polyman test wa-solution                        # diff a named solution against main

polyman remote pull <id> .                      # sync from Polygon
polyman remote push . && polyman remote commit . "msg"
```

Never run a solution by hand-spawning g++ unless you have a specific reason; let polyman compile and execute so time/memory limits are enforced consistently.

## 4. Solution tags — read before editing `Config.json`

Every solution in `Config.json.solutions[]` carries a `tag`. `polyman verify` fails the problem if a solution does not behave the way its tag claims:

| Tag  | Meaning                       | What `verify` expects                          |
| ---- | ----------------------------- | ---------------------------------------------- |
| `MA` | Main correct (reference)      | Passes every test. **Exactly one required.**   |
| `OK` | Alternative correct           | Passes every test.                             |
| `WA` | Wrong answer                  | WA on at least one test.                       |
| `TL` | Time limit exceeded           | TLE on at least one test.                      |
| `TO` | TLE-or-OK                     | Algorithmically correct, may TLE — not strict. |
| `ML` | Memory limit exceeded         | MLE on at least one test.                      |
| `RE` | Runtime error                 | Crashes on at least one test.                  |
| `PE` | Presentation error            | PE on at least one test.                       |
| `RJ` | Rejected (any failure)        | Fails some test, any verdict.                  |

So when adding a wrong/slow/buggy solution, *also* tag it correctly — otherwise `verify` will reject the whole problem.

## 5. `Config.json` — the contract

Open `Config.json`; it is the only configuration file. Important sections:

- `timeLimit` (ms) and `memoryLimit` (MB) — applied to every solution.
- `inputFile` / `outputFile` — `"stdin"` / `"stdout"` for the common case.
- `interactive` — `true` only for interactive problems (rare; needs an interactor).
- `solutions[]` — `{ name, source, tag, sourceType }`. `sourceType` is one of `cpp.g++17`, `cpp.g++20`, `java.11`, `java.17`, `python.3`, `python.pypy3`, etc.
- `generators[]` — `{ name, source, sourceType? }`. Must be C++ (uses testlib).
- `validator` — `{ name, source, testsFilePath?, sourceType? }`. C++ only.
- `checker` — either custom (`{ name, source, isStandard: false, testsFilePath? }`) or standard (`{ name: "ncmp", isStandard: true }`).
- `testsets[]` — usually one named `"tests"` containing a `generatorScript` of `commands`. Each command is either `{ type: "manual", manualFile, group? }` or `{ type: "generator", generator, args?, range?, group? }`. `range: [a, b]` means: run this generator once per integer in `[a, b]`, passing the integer as an argument (this is the seed convention for testlib).

**Whenever you change `solutions[]`, `generators[]`, or `testsets[]`, run `polyman verify` before declaring the change done.** A change to `range`, `args`, or `manualFile` invalidates the existing `tests/` — re-run `polyman generate --all`.

## 6. Workflows for common requests

### "Add a new solution `X`"

1. Drop the source under `solutions/X.{cpp,java,py}`.
2. Add an entry to `Config.json.solutions[]` with the right `tag` (see §4) and `sourceType`.
3. `polyman run X --all` to see how it does.
4. `polyman verify` to confirm tags still match across all solutions.

### "Add a new generator"

1. Write a C++ file in `generators/` that calls `registerGen(argc, argv, 1)` and prints input to `stdout`. The generator is a deterministic function of its CLI args (use `rnd.next(...)` from testlib seeded by args).
2. Add it to `Config.json.generators[]`.
3. Reference it from `testsets[].generatorScript.commands[]`, typically with a `range` for many tests.
4. `polyman generate --all` then `polyman validate --all`.

### "Add a manual sample test"

1. Put the input in `manual/tests/sampleN.txt`.
2. Add `{ type: "manual", manualFile: "./manual/tests/sampleN.txt", group: "samples", useInStatements: true }` to `testsets[].generatorScript.commands[]`.
3. `polyman generate --all`.

### "Tighten the constraints"

1. Update `validator/val.cpp` (`inf.readInt(LO, HI, "name")`).
2. Update `validator/validator_tests.json` to cover the new boundaries.
3. `polyman test validator`.
4. Update statements (`statements/english/input-format.tex` and equivalents).
5. Re-run `polyman generate --all && polyman verify`.

### "Use a standard checker instead of a custom one"

1. `polyman list checkers` to see options. Pick one (`ncmp` for sequences of numbers, `wcmp` for tokens, `yesno`, `dcmp`/`rcmp*` for floats, `lcmp` for line-by-line).
2. In `Config.json`, replace the checker block with `{ "name": "ncmp", "isStandard": true }`.
3. The custom `checker/chk.cpp` becomes unused — keep or delete it.
4. `polyman verify`.

### "Sync to Polygon"

1. `polyman remote register <api-key> <secret>` once.
2. `polyman remote push .` then `polyman remote commit . "msg"`.
3. To grab a fresh copy from Polygon: `polyman remote pull <id> .`.

## 7. Things to *not* do

- **Do not hand-edit files in `tests/`** — they are regenerated by `polyman generate` and your edits will be lost. Put hand-written inputs in `manual/tests/` and reference them.
- **Do not delete or modify `testlib.h`** — `polyman download-testlib` controls it.
- **Do not write tests directly to disk and skip the script** — always go through `Config.json.testsets[].generatorScript`. Polygon needs the script to round-trip.
- **Do not change `inputFile` / `outputFile` to anything other than `"stdin"` / `"stdout"`** unless the user specifically asks — most graders assume stdio.
- **Do not commit binaries.** Compiled artifacts should never be checked in. `.gitignore` should cover them; if it doesn't, ask the user before adding patterns.
- **Do not skip `polyman verify` before declaring work done.** A successful compile is not enough — tag conformance is the real bar.
- **CRLF / LF in JSON test fixtures**: on Windows, validator/checker self-tests in `*_tests.json` may need `\r\n` instead of `\n` inside the embedded `input` strings. Match the OS the user is on.
