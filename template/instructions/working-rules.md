# working-rules.md — How to behave in this problem directory

Read this **before** any non-trivial work. The rules below shape every turn.

## Three modes — pick one per turn

Pick from what the user just said in *this* turn, not earlier ones. Pasting a problem statement is **not** permission to solve it.

| Mode | Trigger | What you do |
| --- | --- | --- |
| **Default** | Statement, idea, observation, complaint, no imperative. | One-line acknowledgement + one short clarifier. **No** algorithm sketch. **No** code. **No** edits. |
| **Thinking** | "solve this", "what approach", "is constraint X reasonable", "thoughts on…", "analyze…". | Algorithm sketch, complexity, edge cases. Pseudocode or ≤5-line snippets. **No file edits.** Stop after the analysis — wait for an explicit "now write it". |
| **Do** | "add", "write", "generate", "fix", "change", "update", "remove", "create", "make", "draft". | Edit the relevant file. Reasoning is internal; visible output is the artifact + one sentence on what changed. |

Ambiguous? **Ask one short question.** Don't guess.

If a previous turn was cancelled or failed: brief acknowledgement and wait. No apology spiral.

## Read before editing

Before you `Edit` or `Write` a file, you must have its current contents in context — you read it this conversation, you wrote it this conversation, or it appeared in a `polyman list …` output. Don't edit blindly. Don't re-read "to be safe" if you already have it.

For batched edits across multiple files: read all of them first, then write all of them.

## Always

- Run `polyman verify` before declaring work done. A successful compile is **not** sufficient. Tag-conformance under `verify` is the bar.
- After a logic change in a generator/validator/checker/solution, **update the matching tests in the same edit**: cases in `validator/validator_tests.json` / `checker/checker_tests.json`. Bug fixes get a regression case. Deleted behavior gets its tests deleted.
- Match constraints across `validator/val.cpp` and `statements/<lang>/input-format.tex`. When you tighten one, tighten the other.
- After changing the script, generator args, manual files, or test indices, re-run `polyman generate --all`.

## Never

- **Hand-edit `testsets/<name>/`.** Regenerated by `polyman generate`; edits get overwritten.
- **Skip the script** by writing tests directly to disk. Polygon needs the script to round-trip.
- **Modify `testlib.h`.** Use `polyman download-testlib` to (re)install.
- **Change `inputFile`/`outputFile` away from `"stdin"`/`"stdout"`** without an explicit ask.
- **Spawn `g++` by hand** instead of using polyman — limits won't be enforced.
- **Commit binaries.** Compiled artifacts never go in git.
- **Run `Edit`/`Write` blindly** without prior `Read`.

## Voice

When discussing or replying to the user (not when writing code in files):

- **Brief.** A clear sentence beats a clear paragraph. End-of-turn: 1-2 sentences on what changed.
- **Push back when something is off.** "n=10⁶ with O(n²) won't fit at TL=1s." Don't agree just to agree.
- **No filler.** "I'll do X now" is filler — just do X. "Let me know if…" is filler.
- **Avoid AI tells:** *absolutely, certainly, definitely, wonderful, fantastic, excellent, remarkable, comprehensive, crucial, essential, facilitate, leverage, utilize, robust, genuinely, truly, literally, extremely.*

If asked "are you an AI?", a brief honest answer is fine; don't derail.

## Workflow checklist (before declaring done)

1. `polyman validate --all` if you touched generators, manual tests, or the validator.
2. `polyman test validator` if you touched the validator.
3. `polyman test checker` if you touched the checker.
4. `polyman verify` if you touched anything affecting solution outcomes (any solution, any test, the checker).

## Useful commands

The most-used set is below. Full per-command reference is in [`commands/`](./commands/index.md) — read only the file for the command you're invoking.

```bash
polyman generate --all                          # regenerate every test
polyman generate --testset tests --index 5      # one test
polyman validate --all                          # validator over every input
polyman run main --all                          # run a solution against every test
polyman test validator                          # validator self-tests
polyman test checker                            # checker self-tests
polyman test wa-solution                        # diff a named solution against main
polyman verify                                  # full pipeline (the bar for "done")
polyman list solutions | generators | checkers | testsets

polyman remote pull <id> .                      # sync from Polygon
polyman remote push . && polyman remote commit . "msg"
```

## When stuck

- testlib API: <https://codeforces.com/blog/entry/18291>
- Standard checker list: `polyman list checkers`
- Worked tutorial: <https://github.com/HamzaHassanain/polyman/blob/master/TUTORIAL.md>

If a polyman command fails confusingly, run the failing component in isolation (`polyman test validator`, `polyman test checker`, `polyman run <sol> --testset tests --index 1`) before changing code.
