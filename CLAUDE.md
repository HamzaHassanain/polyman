# CLAUDE.md — Polyman repo guide for AI agents

You are working on **polyman** (`polyman-cli` on npm), a TypeScript CLI that lets Codeforces problem setters create, test, and sync competitive-programming problems entirely from the terminal. It also drives the Codeforces **Polygon** API.

This file is the fast-path orientation for any AI agent (Claude, Cursor, Aider, Codex, etc.) working in this repo. `AGENTS.md` is a pointer to this file. Read this first; consult the long-form docs only when you need depth.

---

## 1. What polyman does (one paragraph)

`polyman new <dir>` copies `template/` into `<dir>`, producing a problem skeleton with `Config.json`, `solutions/`, `generators/`, `validator/`, `checker/`, `statements/`, and `manual/`. The user fills these in. Then `polyman generate --all` builds tests, `polyman validate --all` runs the validator, `polyman run <sol> --all` runs a solution, and `polyman verify` does the whole pipeline. `polyman remote …` syncs with Polygon over HTTPS using API key + secret.

## 2. Repo layout

```
src/
  cli.ts          Commander.js entry point — every CLI command is wired here
  actions.ts      Top-level action functions called by cli.ts (1700 lines, the orchestration layer)
  steps.ts        Reusable workflow steps composed by actions (1500 lines)
  executor.ts     Process spawning, compilation, time/memory limits (980 lines)
  polygon.ts      Polygon HTTPS API client — sign requests, push/pull problems (1800 lines)
  formatter.ts    chalk-based terminal output (icons, colours, spinners)
  help.ts         Custom `--help` renderer
  types.d.ts      All TypeScript types — Polygon API shapes + local Config.json schema
  helpers/
    checker.ts            Checker compile + self-test
    validator.ts          Validator compile + self-test
    generator.ts          Generator compile + script execution
    solution.ts           Solution compile, run on tests, compare verdicts
    testset.ts            Testset enumeration (testset / group / index)
    script-parser.ts      Parses Polygon-format generator scripts
    create-template.ts    `polyman new` implementation
    testlib-download.ts   Downloads testlib.h from GitHub
    utils.ts              File ops, path resolution, small shared helpers
    remote/               Polygon-side helpers split out of polygon.ts
template/         What `polyman new` copies into a new problem (see template/CLAUDE.md)
assets/checkers/  Standard testlib checkers (ncmp, wcmp, yesno, ...) shipped with the package
dist/             Compiled output — generated by `npm run build`, do not edit
```

The single source of truth for the **on-disk problem schema** is `src/types.d.ts` (look for `ConfigFile`, `LocalSolution`, `LocalGenerator`, `LocalChecker`, `LocalValidator`, `LocalTestset`, `GeneratorScript`). When changing `Config.json` shape, update both the type and `template/Config.json`.

## 3. Build, run, lint

| Task                  | Command                                  |
| --------------------- | ---------------------------------------- |
| Install deps          | `npm install`                            |
| Compile to `dist/`    | `npm run build`                          |
| Run from source       | `npm run dev -- <args>` (uses ts-node)   |
| Run compiled CLI      | `npm start -- <args>` or `node dist/cli.js <args>` |
| Watch-mode build      | `npm run watch`                          |
| Lint                  | `npm run lint`                           |
| Lint + auto-fix       | `npm run lint:fix`                       |
| Format check          | `npm run format:check`                   |
| Format write          | `npm run format`                         |
| Generate TypeDoc      | `npm run docs`                           |

Before declaring any change "done": run `npm run build` **and** `npm run lint`. Both must pass. There is no Jest/Vitest suite in CI right now — verification is done manually with `polyman new` + `polyman verify` against a sample problem.

To smoke-test a change end-to-end:

```bash
npm run build
node dist/cli.js new /tmp/polyman-smoke
cd /tmp/polyman-smoke && node /path/to/polyman/dist/cli.js download-testlib && node /path/to/polyman/dist/cli.js verify
```

## 4. Conventions enforced by tooling

The TS config is strict (`tsconfig.json`): `strict`, `exactOptionalPropertyTypes`, `noImplicitReturns`, `noImplicitOverride`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `noPropertyAccessFromIndexSignature`. ESLint runs `recommendedTypeChecked`. Prettier: single quotes, semicolons, 2-space indent, 80-col, trailing commas `es5`, avoid arrow parens.

- Unused parameters must start with `_` (`argsIgnorePattern: '^_'`).
- Imports are NodeNext ESM-style; `module: nodenext`. Use relative imports with extensions where Node requires them.
- Async functions return `Promise<...>` — `no-misused-promises` is on; do not pass an async function where a sync callback is expected without `void`-wrapping.
- Logging goes through `formatter.ts` (`fmt.info`, `fmt.error`, etc.), not raw `console.log`, except where existing code already uses `console.log` for plain output.

## 5. Mental model: how an action runs

`cli.ts` parses argv → calls a function in `actions.ts` → which orchestrates **steps** from `steps.ts` → which call **helpers** (compile, run, compare) from `helpers/*` → which use **executor.ts** to spawn child processes with time/memory limits. For Polygon commands the action calls into `polygon.ts` instead.

When adding a new command:

1. Define the option/argument shape in `cli.ts`.
2. Add an action in `actions.ts` that translates CLI options into a typed call.
3. Compose it from existing steps where possible — most workflows already exist.
4. Only add to `helpers/` if you need a genuinely new primitive.

When debugging a failing problem run, the layer to look at is usually `executor.ts` (process lifecycle, time-limit enforcement) or `helpers/solution.ts` (verdict comparison).

## 6. Solution tags (the verdict system)

Every solution has a `tag` (`SolutionTag` in `types.d.ts`):

| Tag  | Means                       | `verify` expects                            |
| ---- | --------------------------- | ------------------------------------------- |
| `MA` | Main correct (reference)    | Pass every test. Exactly one required.      |
| `OK` | Alternative correct         | Pass every test.                            |
| `WA` | Wrong answer                | Fail at least one test with WA.             |
| `TL` | Time limit exceeded         | TLE on at least one test.                   |
| `TO` | TLE-or-OK                   | May TLE; not required to fail.              |
| `ML` | Memory limit exceeded       | MLE on at least one test.                   |
| `RE` | Runtime error               | Crash on at least one test.                 |
| `PE` | Presentation error          | PE on at least one test.                    |
| `RJ` | Rejected (any failure)      | Fail somehow on at least one test.          |

`verify` fails the whole problem if a solution does not match its tag. This is enforced in `helpers/solution.ts` via the `VerdictTracker` interface.

## 7. Polygon integration — what to know

`polygon.ts` is a hand-rolled HTTPS client. Every request is signed with a SHA-512 HMAC of the form `apiSig = randomPrefix + SHA512(prefix/method?params#secret)`. Credentials live in a local `~/.polyman/credentials.json` (registered via `polyman remote register`). Do not log secrets. When extending a remote command, follow the existing pattern: build params → `signRequest` → `httpsRequest` → parse JSON envelope.

## 8. Things to be careful with

- **Do not edit `template/` casually.** It is the public surface for new problems and is bundled into the npm package. Any change ripples to every future `polyman new`. If the user asks for a template change, also update `template/CLAUDE.md` and `template/AGENTS.md`.
- **Do not bump dependencies as a side-effect** of unrelated work. The two runtime deps (`chalk@^5`, `commander@^14`) are intentional choices.
- **Windows quirks are real.** Process cleanup on TLE is fragile on Windows (`NOTES.md`). Avoid changes to `executor.ts` process-kill paths without testing on Windows or asking the user.
- **CRLF vs LF in JSON test fixtures**: validator/checker tests embed input as JSON string literals; on Windows these may need `\r\n`. See `NOTES.md`.
- **`assets/checkers/*.cpp`** are upstream testlib standard checkers — don't modify them; treat as vendor.
- **Don't add new top-level docs** (`*.md`) unless the user asks. Five long-form docs already exist (`README`, `GUIDE`, `TUTORIAL`, `DOCUMENTATION`, `NOTES`).
